# Nexus Agent：规划与执行工作流

## 实现范围

服务采用模块化单体，使用 LangChain `create_agent` 的官方 middleware hooks 构建可持久化的 LangGraph。Planner、步骤调度、Executor、Verifier 是职责划分，不是四个独立服务，也不需要同时维护一个外层图和另一个独立会话。

核心流程：用户目标 → 结构化规划 → 程序选择步骤 → 受限工具 Agent → 验证 → 下一步或有限重新规划 → 最终汇总。简单问答和单工具任务走 direct 分支。

`planning/middleware.py` 负责状态转换和执行边界；`planning/service.py` 负责调用模型；`planning/schemas.py` 负责数据契约和计划合法性。运行、模型、工具、MCP、记忆、协议和持久化继续使用已有模块。

## 图节点与状态

- `PlanningMiddleware.before_agent`：调用 Planner，校验计划并初始化任务；同一用户消息的恢复不会重新创建计划。
- `PlanningMiddleware.before_model`：记录单步骤模型调用次数，超过上限停止。
- `model` / `tools`：执行当前步骤；模型只获得本步骤工具定义。程序在工具执行之前检查模型返回的工具调用，越界调用不会执行。
- `PlanningMiddleware.after_model`：工具调用继续原有工具循环；步骤返回结果后，先做工具错误检查，再调用 Verifier。通过后由程序推进下一步，失败时按规则重新规划或停止。
- `PlanningMiddleware.after_agent`：失败状态转换为结构化错误。

这些钩子由框架编译成实际图节点，`jump_to` 为程序控制的图路由，不是要求模型自行遵守一份自然语言计划。

`state.task` 保存 task id、原始目标的规划描述、用户消息 id、计划版本、重新规划次数、当前步骤，以及每步的任务、工具白名单、依赖、成功条件、执行状态、结果和调用次数。检查点由已有 PostgresSaver 保存，无需新建表或 SQL 迁移。

- `thread_id`：会话。
- `run_id`：本次运行，一次取消后继续会产生新 run。
- `task.id`：一个用户目标对应的计划；跨取消、审批和重新规划保持不变。新问题创建新 task。

## 计划与验证契约

Planner 看到当前可用工具的能力摘要，不承担工具参数生成。输出必须通过 Pydantic Schema 和程序校验：最多配置数量的步骤、唯一步骤 id、依赖按拓扑顺序排列、无环、无未知工具。工具为空表示纯模型处理步骤。

当前使用严格 JSON 契约校验，兼容返回 JSON 代码块的模型。无效输出直接返回 `PLANNING_FAILED`，不静默降级为不受计划约束的执行，也不通过无限格式修复增加调用。

Executor 负责单步中的模型与工具循环，依赖原有工具参数校验、预算、超时、重试、人工确认和结构化错误。步骤结果保存在检查点；已完成结果提供给后续步骤和最终汇总。

验证分两层：

1. 程序确认：有工具需求时必须出现工具结果；工具错误状态、`ok=false`、用户拒绝不能当成功；越界工具禁止执行。
2. 模型确认：根据步骤成功条件、执行结果和工具证据输出 `passed/reason`。模型验证不等于事实正确性保证，新增业务工具时应继续补充字段、计算一致性等确定性验证。

步骤产物和 Planner/Verifier 的 JSON 不作为回答流到页面。AG-UI 适配器保留工具调用、审批和结果事件，隐藏步骤执行器的文本与推理草稿，仅最终汇总作为回答展示。

## 重新规划与副作用

只有验证未通过、当前步骤未执行写操作、且仍有重新规划次数时，才能自动重新规划。保留成功步骤，替换剩余步骤，增加计划版本；新步骤可读取成功结果，但不能自动引入写工具。

工具明确失败、被拒绝或结果未知时停止，不尝试通过重新规划绕过拒绝或重复提交。写工具执行后即使验证失败也不会自动换方案重写。

远端写操作与本地检查点之间没有分布式事务。远端已成功、本地尚未保存时崩溃，仍存在结果未知窗口；生产业务写接口需要幂等键、状态查询或人工核实。当前实现不承诺 exactly-once。已有只读注解必须来自服务端工具注册，未知工具按可能写入处理。

## 预算、取消与恢复

规划、执行、验证、重新规划、汇总、摘要和重试共用当前 RunContext 的 LimitTracker。步骤转换不会重置截止时间或预算。辅助模型调用也检查剩余输入预算并记录消耗。

保留原有取消机制。计划执行中从检查点恢复待执行节点，而不是把步骤结果当作最终回答续写；最终汇总中断时仍可按原有机制续写同一条回答。验证阶段取消后可重做验证，已保存的工具结果不重做。任务失败后应发送新问题；自动重新规划不会绕过失败状态。

手动“继续”是一次新 run，沿用既有新运行预算规则；持久化的步骤调用次数与重新规划次数继续保留。当前尚未实现跨多个 run 的统一计费账本和绝对任务截止时间。

## 配置

配置示例在 `agent-server/.env.example`，无需修改现有 `.env` 即默认开启规划：

```dotenv
PLANNER_ENABLED=true
PLANNER_MAX_STEPS=4
PLANNER_MAX_REPLANS=1
EXECUTOR_MAX_MODEL_CALLS=4
AGENT_MAX_ITERATIONS=16
AGENT_TIMEOUT_SECONDS=120
AGENT_TOKEN_BUDGET=40000
```

`PLANNER_ENABLED=false` 可回退原有直接工具 Agent。步骤数限制 1–6、重新规划 0–2、每步模型调用 1–10。上述 AGENT 配置用于未显式传入 AgentLimits 的服务端 Agent；CLI 显式通过已有命令行参数设置预算。费用与工具次数上限仍采用 AgentLimits。

简单问题目前也有一次 Planner 路由调用，direct 分支不做逐步验证。应通过实际任务集评估规划质量、延迟与成本，再决定是否增加经过评估的快速路由。

## 页面和部署边界

页面名为 Nexus Agent，定位通用目标助手。`ACTIVITY_SNAPSHOT(activityType=plan)` 发送安全的计划投影，仅包含目标、步骤说明、状态和版本；历史投影按相同消息 id 更新，刷新后恢复同一份计划。原始结果、工具参数和验证理由不放进计划卡片。

当前执行为串行，MCP 会话和人工询问仍有进程级约束，继续使用单运行入场和单 HTTP worker。尚未引入任务队列、分布式租约、跨进程接管、自动补偿、并行 DAG 执行或大产物对象存储。页面改名不会自动新增搜索、浏览器、文件或业务操作工具；能力以实际工具目录为准。

## 验证

`tests/test_planning.py` 使用真实编译图和确定性模型验证计划合法性、direct 分支、依赖推进、草稿隐藏、工具范围、验证与重新规划上限、共享预算、人工确认、新目标和取消恢复。PostgreSQL 集成测试验证重建图后恢复原 task、保留已完成写操作及计划历史投影。前端 `tests/plans.test.mjs` 验证实时与历史共用的数据契约。

未执行付费模型调用。上线前还应针对实际模型和业务工具建立任务评估集，测量计划有效率、完成率、错误副作用率、延迟与消耗。
